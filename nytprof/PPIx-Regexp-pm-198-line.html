3PPIx::Regexp - Represent a regular expression of some sort
4
5=head1 SYNOPSIS
6
7 use PPIx::Regexp;
8 use PPIx::Regexp::Dumper;
9 my $re = PPIx::Regexp->new( 'qr{foo}smx' );
10 PPIx::Regexp::Dumper->new( $re )
11 ->print();

13=head1 INHERITANCE
14
15C<PPIx::Regexp> is a L<PPIx::Regexp::Node|PPIx::Regexp::Node>.
16
17C<PPIx::Regexp> has no descendants.
18
19=head1 DESCRIPTION
20
21The purpose of the F<PPIx-Regexp> package is to parse regular
22expressions in a manner similar to the way the L<PPI|PPI> package parses
23Perl. This class forms the root of the parse tree, playing a role
24similar to L<PPI::Document|PPI::Document>.
25
26This package shares with L<PPI|PPI> the property of being round-trip
27safe. That is,
28
29 my $expr = 's/ ( \d+ ) ( \D+ ) /$2$1/smxg';
30 my $re = PPIx::Regexp->new( $expr );
31 print $re->content() eq $expr ? "yes\n" : "no\n"
32
33should print 'yes' for any valid regular expression.
34
35Navigation is similar to that provided by L<PPI|PPI>. That is to say,
36things like C<children>, C<find_first>, C<snext_sibling> and so on all
37work pretty much the same way as in L<PPI|PPI>.
38
39The class hierarchy is also similar to L<PPI|PPI>. Except for some
40utility classes (the dumper, the lexer, and the tokenizer) all classes
41are descended from L<PPIx::Regexp::Element|PPIx::Regexp::Element>, which
42provides basic navigation. Tokens are descended from
43L<PPIx::Regexp::Token|PPIx::Regexp::Token>, which provides content. All
44containers are descended from L<PPIx::Regexp::Node|PPIx::Regexp::Node>,
45which provides for children, and all structure elements are descended
46from L<PPIx::Regexp::Structure|PPIx::Regexp::Structure>, which provides
47beginning and ending delimiters, and a type.
48
49There are two features of L<PPI|PPI> that this package does not provide
50- mutability and operator overloading. There are no plans for serious
51mutability, though something like L<PPI|PPI>'s C<prune> functionality
52might be considered. Similarly there are no plans for operator
53overloading, which appears to the author to represent a performance hit
54for little tangible gain.
55
56=head1 NOTICE
57
58The use of this class to parse non-regexp quote-like strings was an
59experiment that I consider failed. Therefore this use is B<deprecated>
60in favor of L<PPIx::QuoteLike|PPIx::QuoteLike>. As of version 0.058_01,
61the first use of the C<parse> argument to L<new()|/new> resulted in a
62warning. As of version 0.062_01, all uses of the C<parse> argument
63resulted in a warning. After another six months, the C<parse> argument
64will become fatal.
65
66The author will attempt to preserve the documented interface, but if the
67interface needs to change to correct some egregiously bad design or
68implementation decision, then it will change. Any incompatible changes
69will go through a deprecation cycle.
70
71The goal of this package is to parse well-formed regular expressions
72correctly. A secondary goal is not to blow up on ill-formed regular
73expressions. The correct identification and characterization of
74ill-formed regular expressions is B<not> a goal of this package, nor is
75the consistent parsing of ill-formed regular expressions from release to
76release.
77
78This policy attempts to track features in development releases as well
79as public releases. However, features added in a development release and
80then removed before the next production release B<will not> be tracked,
81and any functionality relating to such features B<will be removed>. The
82issue here is the potential re-use (with different semantics) of syntax
83that did not make it into the production release.
84
85From time to time the Perl regular expression engine changes in ways
86that change the parse of a given regular expression. When these changes
87occur, C<PPIx::Regexp> will be changed to produce the more modern parse.
88Known examples of this include:
89
90=over
91
92=item C<$(> no longer interpolates as of Perl 5.005, per C<perl5005delta>.
93
94Newer Perls seem to parse this as C<qr{$}> (i.e. and end-of-string or
95newline assertion) followed by an open parenthesis, and that is what
96C<PPIx::Regexp> does.
97
98=item C<$)> and C<$|> also seem to parse as the C<$> assertion
99
100followed by the relevant meta-character, though I have no documentation
101reference for this.
102
103=item C<@+> and C<@-> no longer interpolate as of Perl 5.9.4
104
105per C<perl594delta>. Subsequent Perls treat C<@+> as a quantified
106literal and C<@-> as two literals, and that is what C<PPIx::Regexp>
107does. Note that subscripted references to these arrays B<do>
108interpolate, and are so parsed by C<PPIx::Regexp>.
109
110=item Only space and horizontal tab are whitespace as of Perl 5.23.4
111
112when inside a bracketed character class inside an extended bracketed
113character class, per C<perl5234delta>. Formerly any white space
114character parsed as whitespace. This change in C<PPIx::Regexp> will be
115reverted if the change in Perl does not make it into Perl 5.24.0.
116
117=item Unescaped literal left curly brackets
118
119These are being removed in positions where quantifiers are legal, so
120that they can be used for new functionality. Some of them are gone in
1215.25.1, others will be removed in a future version of Perl. In
122situations where they have been removed,
123L<perl_version_removed()|PPIx::Regexp::Element/perl_version_removed>
124will return the version in which they were removed. When the new
125functionality appears, the parse produced by this software will reflect
126the new functionality.
127
128B<NOTE> that the situation with a literal left curly after a literal
129character is complicated. It was made an error in Perl 5.25.1, and
130remained so through all 5.26 releases, but became a warning again in
1315.27.1 due to its use in GNU Autoconf. Whether it will ever become
132illegal again is not clear to me based on the contents of
133F<perl5271delta>. At the moment
134L<perl_version_removed()|PPIx::Regexp::Element/perl_version_removed>
135returns C<undef>, but obviously that is not the whole story, and methods
136L<accepts_perl()|PPIx::Regexp::Element/accepts_perl> and
137L<requirements_for_perl()|PPIx::Regexp::Element/requirements_for_perl>
138were introduced to deal with this complication.
139
140=item C<\o{...}>
141
142is parsed as the octal equivalent of C<\x{...}>. This is its meaning as
143of perl 5.13.2. Before 5.13.2 it was simply literal C<'o'> and so on.
144
145=back
146
147There are very probably other examples of this. When they come to light
148they will be documented as producing the modern parse, and the code
149modified to produce this parse if necessary.

176=head2 new
177
178 my $re = PPIx::Regexp->new('/foo/');
179
180This method instantiates a C<PPIx::Regexp> object from a string, a
181L<PPI::Token::QuoteLike::Regexp|PPI::Token::QuoteLike::Regexp>, a
182L<PPI::Token::Regexp::Match|PPI::Token::Regexp::Match>, or a
183L<PPI::Token::Regexp::Substitute|PPI::Token::Regexp::Substitute>.
184Honestly, any L<PPI::Element|PPI::Element> will work, but only the three
185Regexp classes mentioned previously are likely to do anything useful.
186
187Whatever form the argument takes, it is assumed to consist entirely of a
188valid match, substitution, or C<< qr<> >> string.
189
190Optionally you can pass one or more name/value pairs after the regular
191expression. The possible options are:
192
193=over
194
195=item default_modifiers array_reference
196
197This option specifies a reference to an array of default modifiers to
198apply to the regular expression being parsed. Each modifier is specified
199as a string. Any actual modifiers found supersede the defaults.
200
201When applying the defaults, C<'?'> and C<'/'> are completely ignored,
202and C<'^'> is ignored unless it occurs at the beginning of the modifier.
203The first dash (C<'-'>) causes subsequent modifiers to be negated.
204
205So, for example, if you wish to produce a C<PPIx::Regexp> object
206representing the regular expression in
207
208 use re '/smx';
209 {
210 no re '/x';
211 m/ foo /;
212 }
213
214you would (after some help from L<PPI|PPI> in finding the relevant
215statements), do something like
216
217 my $re = PPIx::Regexp->new( 'm/ foo /',
218 default_modifiers => [ '/smx', '-/x' ] );
219
220=item encoding name
221
222This option specifies the encoding of the regular expression. This is
223passed to the tokenizer, which will C<decode> the regular expression
224string before it tokenizes it. For example:
225
226 my $re = PPIx::Regexp->new( '/foo/',
227 encoding => 'iso-8859-1',
228 );
229
230=item parse parse_type
231
232This option specifies what kind of parse is to be done. Possible values
233are C<'regex'>, C<'string'>, or C<'guess'>. Any value but C<'regex'> is
234experimental.
235
236As it turns out, I consider parsing non-regexp quote-like things with
237this class to be a failed experiment, and the relevant functionality is
238being deprecated and removed in favor of
239L<PPIx::QuoteLike|PPIx::QuoteLike>. See above for details.
240
241If C<'regex'> is specified, the first argument is expected to be a valid
242regex, and parsed as though it were.
243
244If C<'string'> is specified, the first argument is expected to be a
245valid string literal and parsed as such. The return is still a
246C<PPIx::Regexp> object, but the
247L<regular_expression()|/regular_expression> and L<modifier()|/modifier>
248methods return nothing, and the L<replacement()|/replacement> method
249returns the content of the string.
250
251If C<'guess'> is specified, this method will try to guess what the first
252argument is. If the first argument is a L<PPI::Element|PPI::Element>,
253the guess will reflect the PPI parse. But the guess can be wrong if the
254first argument is a string representing an unusually-delimited regex.
255For example, C<'guess'> will parse C<"foo"> as a string, but Perl will
256parse it as a regex if preceded by a regex binding operator (e.g. C<$x
257=~ "foo">), as shown by
258
259 perl -MO=Deparse -e '$x =~ "foo"'
260
261which prints
262
263 $x =~ /foo/u
264
265under Perl 5.22.0.
266
267The default is C<'regex'>.
268
269=item postderef boolean
270
271This option is passed on to the tokenizer, where it specifies whether
272postfix dereferences are recognized in interpolations and code. This
273experimental feature was introduced in Perl 5.19.5.
274
275The default is the value of
276C<$PPIx::Regexp::Tokenizer::DEFAULT_POSTDEREF>, which is true. When
277originally introduced this was false, but was documented as becoming
278true when and if postfix dereferencing became mainstream. The intent to
279mainstream was announced with Perl 5.23.1, and became official (so to
280speak) with Perl 5.24.0, so the default became true with L<PPIx::Regexp>
2810.049_01.
282
283Note that if L<PPI|PPI> starts unconditionally recognizing postfix
284dereferences, this argument will immediately become ignored, and will be
285put through a deprecation cycle and removed.
286
287=item strict boolean
288
289This option is passed on to the tokenizer and lexer, where it specifies
290whether the parse should assume C<use re 'strict'> is in effect.
291
292The C<'strict'> pragma was introduced in Perl 5.22, and its
293documentation says that it is experimental, and that there is no
294commitment to backward compatibility. The same applies to the
295parse produced when this option is asserted. Also, the usual caveat
296applies: if C<use re 'strict'> ends up being retracted, this option and
297all related functionality will be also.
298
299Given the nature of C<use re 'strict'>, you should expect that if you
300assert this option, regular expressions that previously parsed without
301error might no longer do so. If an element ends up being declared an
302error because this option is set, its C<perl_version_introduced()> will
303be the Perl version at which C<use re 'strict'> started rejecting these
304elements.
305
306The default is false.
307
308=item trace number
309
310If greater than zero, this option causes trace output from the parse.
311The author reserves the right to change or eliminate this without
312notice.
313
314=back
315
316Passing optional input other than the above is not an error, but neither
317is it supported.
318
319=cut

361=head2 new_from_cache
362
363This static method wraps L</new> in a caching mechanism. Only one object
364will be generated for a given L<PPI::Element|PPI::Element>, no matter
365how many times this method is called. Calls after the first for a given
366L<PPI::Element|PPI::ELement> simply return the same C<PPIx::Regexp>
367object.
368
369When the C<PPIx::Regexp> object is returned from cache, the values of
370the optional arguments are ignored.
371
372Calls to this method with the regular expression in a string rather than
373a L<PPI::Element|PPI::Element> will not be cached.
374
375B<Caveat:> This method is provided for code like
376L<Perl::Critic|Perl::Critic> which might instantiate the same object
377multiple times. The cache will persist until L</flush_cache> is called.

470=head2 delimiters
471
472 print join("\t", PPIx::Regexp->new('s/foo/bar/')->delimiters());
473 # prints '// //'
474
475When called in list context, this method returns either one or two
476strings, depending on whether the parsed expression has a replacement
477string. In the case of non-bracketed substitutions, the start delimiter
478of the replacement string is considered to be the same as its finish
479delimiter, as illustrated by the above example.
480
481When called in scalar context, you get the delimiters of the regular
482expression; that is, element 0 of the array that is returned in list
483context.
484
485Optionally, you can pass an index value and the corresponding delimiters
486will be returned; index 0 represents the regular expression's
487delimiters, and index 1 represents the replacement string's delimiters,
488which may be undef. For example,
489
490 print PPIx::Regexp->new('s{foo}<bar>')->delimiters(1);
491 # prints '<>'
492
493If the object was not initialized with a valid regexp of some sort, the
494results of this method are undefined.
495
496=cut
497
498sub delimiters {
499 my ( $self, $inx ) = @_;
500
501 my @rslt;
502 foreach my $method ( qw{ regular_expression replacement } ) {
503 defined ( my $obj = $self->$method() ) or next;
504 push @rslt, $obj->delimiters();
505 }
506
507 defined $inx and return $rslt[$inx];
508 wantarray and return @rslt;
509 defined wantarray and return $rslt[0];
510 return;
511}
